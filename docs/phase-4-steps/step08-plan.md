# Step 8 plan: `@dzgrid/core/detail`, the detail rows and the sparse layout (lead, 2026-10-21)

Plan: `docs/phase-4-plan.md` D2 (detail part), D7, D8, D9, step 8, risks (« scaled scrolling with unequal heights », « nested grids »); owner Q4 (fixed 240 px by default, configurable), Q5 (2 levels tested, soft cap 3; no tree and detail on one grid); spike S12 (`spikes/s12-variable-heights/`, verdict « go, no cap »; its `sparse-layout.ts` is a throwaway: rewritten, not copied). Sheet: `docs/behaviors/master-detail.md` stands (written at step 1). Clean room: behaviour only.

## Decisions and reasons

1. **One entry, two files.** `@dzgrid/core/detail` (`packages/core/src/detail.ts`) re-exports `detail/shape.ts` (`detailShape`, `detailConflicts`) and `detail/layout.ts` (`sparseRowLayout`). Pure, no platform; types only from the model. Budget 1 000 over the core (owner Q7). The base never imports it; it imports no tree, server, span or csv module (layering test).
2. **API.** `detailShape<T>({ height?, initial?, sizes? })` → a `RowShape` of `kind: 'detail'`. `height`: a number (default 240, owner Q4), `(master) => number`, or `'auto'` (240 until measured). A height that is not a finite number ≥ 0, or a function that throws, gives 240: bad data never throws. `initial`: `'none'` (default) or `'all'` (every row open at the first non-empty load; a depth means nothing without levels). `sizes`: the heights measured by master key, a live map the DOM owns for `'auto'` (point 11).
3. **The rows.** `build` lays one `DetailNode` (key `x:` + the master's key, `kind: 'detail'`, `level` the master's: 0, as a tree is refused beside details, `master`, `data` the master's data) right after each open master, over the order the model hands it: the filtered, sorted rows, or the page cut from them. The data rows are the base's own `flatDisplayed` over that order (a new one per build: its index of keys is made on the first lookup, O(n) for a sorted million, 1.5 ms measured; caching it across toggles did not fit the budget, point 13); the open masters are their positions, sorted (`Uint32Array`), the detail rows' display indices `m[j] + j + 1`. `nodeAt`, `keyAt`, `indexOf` (a data key or a detail key), `nextData` (the flat rows' neighbour: over a detail, from a detail its master's), `parentOf` (a detail's master: the kernel's focus fallback puts the focus on the master when its detail closes), `dataCount` (the data rows: select-all and the header box never count a detail), `details` (the display indices) and `heights` (theirs), the layout's input as they are. Out of bounds: the flat rows' `RangeError`.
4. **Expansion.** The kernel's `rows.expand`, `rows.expandAll`, `rowExpanded` as they are: a master « expanded » is a master whose detail shows. `opens(key)`: a data row the store holds (a detail key, a filler key or an unknown key is a no-op). `parents(snap, depth, shown)`: every held row (`initial: 'all'`, `expandable`), or, `shown`, the data rows of the last build (expand-all opens the rows of the page or the filter shown). **Base change**: the filter's layer (tree-filter.md: toggles under a filter belong to it) is a tree's only — a detail opened under a filter stays open when the filter changes, and collapse-all empties the whole set, filtered or not (D1: the expansion lives apart from the query).
5. **Paging (D2).** **Base change**: the client cuts the page first, then hands the cut to the shape; a tree still refuses pages before that. So a detail follows its master on the same page and is never counted as a page row (the page size, the page count and the footer count data rows only).
6. **Never data.** Selection: the kernel's `isDataKey` guards already skip `x:` keys (select-all, ranges, toggles refused as unknown); `dataCount` keeps the header box right. CSV: `chunks.ts` already skips a detail; `csvRows(…, 'displayed').count` now leaves details out too (`k < 'l'`: keys `d:` and `g:` are written, `l:` and `x:` never — one comparison, the only form that fits `core/csv`'s 3 B). `allRows` (scopes `all`, `selected`) of a shape with no `all()` is, after a **base change**, the flat filtered sorted rows: no detail in it. Copy, paste, edit, `rowClicked`: the DOM (`kind !== 'data'`, step 9–10).
7. **`counts.displayed`** stays « the rows shown », details included as a tree's fillers are (a tree conformance case pins it); « not counted » is the page, the select-all and the export counts (point 5, 6).
8. **Refused beside** (D9, Q5): `detailConflicts({ spans?, tree? })` → `unsupported-combination` warnings, paths `spans` and `tree`, detail `detail` (as `treeConflicts`); the grid (DOM, step 10) tells them and shows the detail without the other.
9. **Nesting cap** (Q5): the nested grid declares its depth to `detailConflicts({ depth })`; past 3, `unsupported-combination` (warning, path `detail.depth`, detail the depth), told by that grid (DOM, step 10, beside the other conflicts), which still works (soft cap). Not in the shape's `problems` (bytes, point 13), and no new problem code (a code is base bytes plus a conformance case per code; « too deep » is a combination of the grid with its parents).
10. **`sparseRowLayout(rows, h, { at, heights })`** (D7, S12): a `RowLayout` where every row is `h` tall except the rows at `at` (display indices, strictly increasing, in `[0, count)`: trusted, the shape makes them; checking them did not fit, point 13) of `heights` (finite, ≥ 0, else `RangeError`, as `PrefixSums`; a missing one too). Memory O(D): the heights and the prefix sums of `height − h`. `offsetOf(i) = i·h + pre[below(i)]` (binary search), `heightOf`, `indexAt` (the last extra starting at or before the offset by binary search, then a division; clamped to the rows; `total` and beyond → the last row; NaN or below 0 → the first), `setHeight` O(D) (the sums from the changed row on), `setHeights(pairs)` one batch recomputed once from the lowest row set (S12's note: group the `'auto'` changes of a frame; true when a height was set to another value on the way), `total`. A row that is not an extra keeps its height. Exact against a brute-force oracle for integer and half-pixel heights.
11. **Heights in the rows.** Each build gives the open details' heights (`rows.heights`: a measure in `sizes`, else `height`: the number, the function of the master, or 240), so the DOM (step 9, `g.layoutFor`) builds `sparseRowLayout(rows, h, { at: rows.details, heights: rows.heights })`. `'auto'`: the DOM keeps its measures in the `sizes` map it handed the shape (kept after a close: a reopened panel starts at its last height) and sends a frame's new ones to the current layout in one `setHeights`; the next build reads them from the map. (A first draft had `shape.layout()` and `shape.measure()`: over budget, point 13.)
12. **What stays for steps 9–10**: the layout seam in the paint, the detail row's cell, `whole` moves, the part slot, ResizeObserver, the nested-grid LRU, the server model with details (a source's inner client model gets the shape through `ModelEnv.shape`, untested here).

13. **Budget (1 000 B over the core, never raised).** The first full version measured 1 452 B. Cut to fit, in order: `measure`/`layout` methods out of the shape (heights in the rows, `sizes` from the DOM), the data rows' cache across toggles, `at`'s checks in the layout, the nesting problem moved from the shape to `detailConflicts`, `opens` by key form (a data key; the kernel refuses an unknown one), the bounds check left to the flat rows. Measured 994 (`check:size`).
