Plan: `docs/phase-4-plan.md` D10, step 7, risks (« lazy loading and the gate: per-parent channels, epoch kills all, collapse during a request, collapse everything on epoch »); owner Q6 « Les deux ». Sheet: `docs/behaviors/tree-lazy.md` (new, written first); `tree-view.md`, `tree-keys.md`, `tree-filter.md` stand. Clean room: behaviour only (WAI-ARIA 1.2, APG treegrid, public docs of what a user sees).

## Decisions and reasons

1. **Where the code goes (budgets).** `@dzgrid/core/tree` has 139 B left of 3 500 and `@dzgrid/dom/tree` 195 B of 2 600: the loader does not fit there (the step's call allows a separate entry). So two new entries, each a wrapper the host opts into: `@dzgrid/core/tree-lazy` (`lazyShape(treeShape, { has, load })`: the loading rows, the request state, the cache; pure, no platform) and `@dzgrid/dom/tree-lazy` (`lazyChildren({ has, load })`: the core wrapper plus the DOM part: the loading and error rows' text, Retry by click and Enter, announcements, the window's `AbortController`). `tree()` takes `lazy?: LazyChildren`: a grid without it carries none of it. `@dzgrid/core/tree` only gains `kidsOf(key)` on its rows (the children a row holds, whatever the filter: ≈ 25 B). Their budgets are new entries, measured + 10 % (an owner decision to confirm, not a raise).
2. **API names** (« decide, keep short »): `tree({ parentId, lazy: lazyChildren({ has(row), load(row, { signal }) }) })` rather than `tree({ hasChildren, loadChildren })`: the options must live in the opt-in entry (reason 1). B: `sourceRows({ fetch, children(req: ChildRequest) })`.
3. **The loading row is a view of state, not a request.** The wrapper's `build` puts one `kind: 'loading'` node (key `l:<parent key>`) under each open declared parent that holds no child and has not answered (`failed: true` after a failure). After each change of the model, the controller starts a request for a loading row without one and aborts a request whose row is gone. So: one request per shown loading row, never two; every request answered or aborted; collapse, a closed ancestor, a filter or a removal all abort by the same rule. Same key loading and failed: the focus stays through failure and retry.
4. **Seams in the base** (`@dzgrid/core`, ≈ +60 B): `RowShape.attach?(model, redraw)` called once by `clientRows` (the controller subscribes, applies answers with `applyTransaction`, redraws on a failure or an empty answer), `RowShape.refresh?()` called first by `invalidate` (the loaded rows removed), `ModelEnv.shape` (a server's inner model gets the tree), the `LoadingNode` type in the `RowNode` union. The `load` hook (already there for nested rows) tells the wrapper a `setRows`: every load forgotten before the build.
5. **Answers through the transaction path**, source `data`: placed by their own parent id or path, sorted and filtered like any row; duplicates told by the store. An empty answer (or all refused) leaves a leaf. Nested arrays (`children`) with `lazy`: refused (`unsupported-combination`, path `tree.lazy`), the tree shown without lazy loading (a loaded row could not name its parent).
6. **Stale answers**: a token per request (the state object): an answer whose state is no longer the current one is dropped (closed, reset, retried, `setRows`). For B the gate decides first (channel `children:<parent key>`, epoch).
7. **Cache**: the store is the cache. `setRows` forgets the cache (answered parents) but not a load running whose loading row still shows: it goes on (the rows request of a server answering after a refresh would otherwise restart every child request; a `setRows` that changes nothing gives no rebuild, so aborting there would leave a loading row with no request); `refresh` removes the rows the loads brought (ids kept by the controller, from the model's `getRowId` handed to the `load` hook), forgets every load, and the open parents load again. A row loaded with no child is a leaf until then.
8. **Filters** apply to loaded rows only (D4 unchanged); a declared row hidden by a filter is not loaded. `kidsOf` (structure, not the filtered view) decides « holds no child »: a declared row whose loaded children are all filtered out is a leaf, not loaded again.
9. **Expand-all and `*`** pass over rows not loaded (`parents()` and `childrenAt > 0` unchanged): no burst of requests. Collapse-all closes them (an open loading row is a parent shown).
10. **Events and words**: `rowExpanded` stays the action's (never the load). Announcements: an opening that shows a loading row says `announce.loading`; the answer says `tree.expanded {name, n}`; a failure `announce.error`; a retry `announce.loading`. The row texts are the base bundle's `grid.loading`, `grid.error`, `grid.retry`: the tree bundles (149/182/240 of 200/220/250; Arabic 10 B left) get nothing new.
11. **Focus**: a focus on the loading row goes, when the children arrive, to the first child (the row now at its place: `parentOf` of a loading key answers null when its parent shows children); when its parent closes or answers no child, to the parent. ← on a loading or error row: its parent.
12. **B: server children.** `DataSource.children?(req: ChildRequest)`; the request carries `parent` (key), `id`, `row`, the server's part of the query as sent for rows (`filter` wire form, `quick`, `sort`, `params`, `zone`), `epoch`, `key` (canonical, without the row) and `signal`; answer `T[]` or `{ rows }`. The inner client model gets the tree shape (`ModelEnv.shape`); the source model forwards the expansion API and tells the inner model's own changes (a toggle, an answer) as its changes. A new epoch: `gate.newEpoch()` aborts every channel, the controller forgets, every row closes (`setExpansion(∅)`, no `rowExpanded`). A collapse cancels the parent's channel (`gate.cancel`): its answer is dropped as `aborted`.
13. **Paging + server tree: roots paged, children whole.** The server's pages count roots (the rows request is unchanged); a child request has no page. Reason: it is what a page of a server tree means to a user, it costs nothing (a page answer replaces the rows; the loads are forgotten as on any `setRows`), and refusing would leave a large server tree with no way to page. Browser pages + tree stay refused (D2).
14. **Server rows are matches**: the server filters; its rows are not muted (it cannot say which are ancestors only). Written in the sheet.
