## 1. Facts that shape the design (read in the code at `e6a1299`)

1. **One server model today, two modes.** `sourceRows(data, o)` (`packages/core/src/server/rows.ts:65-69`) makes a `SourceModel` (`kind: 'source'`, `client.ts:67`, `:883-889`) that wraps an inner client model (`rows.ts:147`). With server pages it holds **one page** in it; with `operations.page` `'off'` or `'client'` it fetches **the whole set** once (`rows.ts:311-321`), kept even above `maxRows` (100 000 by default, `rows.ts:27`, `:95`, warning `fetched-set-large`). There is no third mode: a list too long to fetch whole can only be paged. Every answer replaces the inner model's rows (`inner.setRows`, `rows.ts:319`, `:361`): the inner model holds what is shown, nothing else.
2. **The request is already a window.** `DataRequest` (`server/source.ts:76-89`) carries the server's part of the query (wire filter, quick, sort), `params`, `zone`, a canonical `key`, the `signal`, and with server pages a `PageWindow { index, size, offset, cursor }` (`source.ts:92-97`). `DataResponse { rows, total?, hasNext?, nextCursor? }` (`source.ts:104-109`). **ARCH's `BlockRequest { startRow, endRow }` is exactly `page.offset` / `offset + size`, and `lastRow` is `total`**: a host that answers server pages by offset already answers blocks. Cursor paging reaches only pages already reached (`rows.ts:170-171`, `:556`): no jump, so no thumb drag to row 5 000 000.
3. **The gate is per channel and per epoch** (`server/gate.ts`): `begin(channel, key)` aborts the channel's previous request (`:94-106`), `cancel(channel)` (`:119-126`), `newEpoch()` aborts every channel (`:127-131`), `settle` decides once (`:108-118`). Channels in use: `rows`, `values:<col>` (`rows.ts:491-506`), `children:<key>` for the lazy tree (`rows.ts:254-262`). It has no limit on channels and no notion of « how many at once »: a block channel per block fits as is; **concurrency and scheduling must live in the block store, not in the gate**. Conformance: `conformance/cases/server-gate/*` (22 cases, none about many sibling channels of one kind) and `source-model/*` (36 cases). Node perf line « gate begin/accepts x 100 000 » 6.5 ms (`perf/budgets.json:69`).
4. **Epochs and purges exist.** `restart()` (`rows.ts:392-408`): a new server query, zone, params or source → `gate.newEpoch()`, the lazy tree reset, the expansion emptied, index 0, counts forgotten, one `query` change, one load. `invalidate({ purge })` (`rows.ts:566-584`) empties the rows (the overlay shows), else `again()` asks the page shown again with the rows kept (the busy bar). `hold(fn)` (`rows.ts:598-609`, Phase 6 E5-1): the loads asked meanwhile become one request (state restore, `@dzgrid/dom/state`).
5. **Displayed rows are an interface, not an array.** `DisplayedRows` (`core/src/row/displayed.ts:10-26`): `count`, `nodeAt`, `keyAt`, `indexOf`, `index`, `nextData`, optional `dataCount`, `levelAt`, `parentOf`. A virtual list of 10⁷ rows whose unloaded positions return a loading node is possible without touching the type — but **eight places walk every displayed row** and would walk 10⁷: `kernel.ts:649` (`selection.allDisplayed`), `:715` and `:890` (`headerState` / `headerSelection` under a selection rule or `selectAll: 'displayed'`), `dom/src/interact/select.ts:26` (Shift+click and page ticking), `dom/src/pagination/context.ts:93` (the strip's counts), `dom/src/row-numbers/index.ts:62` (numbering past details), `dom/src/find/index.ts:150` (Ctrl+F), `dom/src/print/index.ts:104` (print), plus `core/src/csv/rows.ts:38` (the CSV of `displayed`). Under `selectAll: 'query'` (server pages) the kernel takes the query path (`kernel.ts:632`, `:635`) and avoids the first three — except under a selection rule (`gate?.on`, `kernel.ts:632`, `:708`), which takes the rows shown.
6. **Loading rows exist, for the lazy tree only.** `RowKind` has `'loading'` (`row/node.ts:3`); `LoadingNode { key: 'l:' + parent, kind, level, parent, failed }` (`node.ts:63-74`, made at `tree/lazy.ts:209`) — `parent` is required. It is never data (`isDataKey` takes `d:` only, `ids.ts:135`), never exported (`csv/rows.ts:41`: `l:` sorts after `d:`, `f:`, `g:`), not counted in `dataCount`. **Only the tree painter draws it** (`dom/src/tree/index.ts:290` `aria-busy`, `:318-320` text and Retry through `tree/lazy.ts`): the DOM base draws a loading node as an empty row. The sheet `tree-lazy.md` already fixes its accessibility (l. 15–25, 40–48: « Chargement… », `aria-busy="true"`, `aria-setsize="-1"`, the same key through failure and retry, a focus on it goes to the row that takes its place, only user actions announced).
7. **Focus survives a row replaced at the same index**: the kernel's fallback gives the focus to « the row now at its index » (`conformance/cases/focus-fallback/removed-middle.json`). A focused loading row replaced by its block's data row keeps the focus at that position with no new code.
8. **The paint knows the window, the model does not.** `RowModel` (`model/client.ts:66-176`) has no `rangeNeeded` (ARCH §3.6 l. 1140 planned one): the paint computes `w.rows.first..last` (`dom/src/render/viewport.ts:289-290`) and hands features a `Frame` (`render/rows.ts:116-141`) **without** the window; features see it only through `afterRows` (`viewport.ts:321`). A model that loads what is on screen needs a seam in the DOM base: the window told to the model after each paint.
9. **10⁷ rows scroll today.** `scrollMapper` caps the physical height at `MAX_PHYSICAL = 4 000 000` px (`core/src/layout/scroll-mapper.ts:10`) and projects the scroll range, ends exact; spike S1 (ROADMAP l. 55): no row cap, row 999 999 reached with 0 px error, Firefox collapses above 17.9 M px. At 32 px a row, 10⁷ rows are 3.2·10⁸ logical px: the thumb moves ~80 logical px per physical px (2–3 rows); wheel and keys move by logical offsets. `uniformRowLayout` is O(1) per row. **A known total is needed to size the scroll range**: with an unknown one the list can only grow as it is scrolled.
10. **The overlay and the busy bar.** `overlayPainter` (`dom/src/render/overlay.ts:55-89`): a server's loading shows the overlay only when nothing is displayed (`:58`), else the busy bar after 200 ms, held 400 ms (`:40-54`, `:64`); `aria-busy` on the grid at once and `data-stale` on the root while rows are kept (`viewport.ts:249-252`); nothing announced for a busy reload (`overlays.md` l. 26). A grid that keeps loading blocks while scrolling would hold `aria-busy` and `data-stale` (rows « stale ») most of the time: **block loads must not count as the model's `loading` phase**, which today means « the rows shown are being replaced ».
11. **Counts and `aria-rowcount`.** Server pages: `counts.filtered` = the server's total or null (`rows.ts:459`); `aria-rowcount` = rows shown + header rows (`viewport.ts:243`; `server-pagination.md` l. 23: never the server total). A scrolled list shows every row of the total in one grid: its `aria-rowcount` is the total (+ headers), or **-1 when unknown** (ARIA 1.2), and `aria-rowindex` runs to 10⁷.
12. **Selection across pages is query-tied.** `selectAll: 'query'` and `keeps: () => true` under server pages (`rows.ts:461-462`); `membershipOf` = the wire filter + quick + browser part + params (`rows.ts:464-467`); « all » is an everything-except selection tied to it (ARCH « Appartenance » l. 136–139: header box states, `selectionChanged.scope`, `kernel.selectionScope`). A block model can take these three policies unchanged: « select all 10⁷ rows » never loads them.
13. **Exports and print on a server.** `csvRows` returns null when the model has no `allRows` (`csv/rows.ts:32-35`); then `all` and `selected` go to the host's `exportAll` with an `ExportRequest` carrying the server's part of the query without the page (`csv/rows.ts:12-23`, `dom/src/export/run/request.ts:47-56`, `run/index.ts:182-191`; `missing-feature` without it). `displayed` writes the rows shown (the page). Print prints the rows shown, 5 000 at most (`print-too-many`; `print/index.ts:55`, `:104`). Ctrl+F searches « the loaded page only, said in the bar » on a source (`find/index.ts:121-124`, `:198`).
14. **Grouping refuses a server today** (Phase 7 D16, owner Q-SRV A): `dom/grouping` steps aside on `g.rows.kind === 'source'` (`dom/src/grouping/index.ts:86-93`), `GroupShape.off()` (`core/src/grouping/shape.ts:40`), problem `unsupported-combination` path `source` (`shape.ts:500`). What Phase 7 built and Phase 8 can reuse for server groups: typed group keys `g:` + column id + type tag + canonical value (`ids.ts:72-75`, Phase 7 D3) — a group key is its values, never in a `Problem` or the state; `GroupNode { column, value, count, aggs }` and `FooterNode` (`node.ts:22-52`); the painter reads `TreeRows` (`posAt`, `sizeAt`, `childrenAt`, `expandedAt`, `levelAt`, `parentOf`; `core/src/tree/shape.ts:24-37`), so **a server's displayed rows that implement `TreeRows` get the group painter, keys, `aria-*`, sentences and sticky groups as they are**; `rowGroups` in the state (Phase 7 D17) and `[(groupBy)]` in Angular (`packages/angular/src/grid.ts:175`, `:402-415`).
15. **The lazy tree on a server** (Phase 4 step 7, ARCH l. 409–415): `DataSource.children` per parent, channel `children:<key>`, every child at once, never paged; server pages + tree: pages count roots. A server group of 50 000 leaves cannot load « whole »: **lazy groups need children in blocks**, not the tree-lazy loader.
16. **Transactions.** The client model has `applyTransaction` (`model/client.ts`, `ClientModel`); the source model has none: a host's live update on a server grid is `refresh()` (`kernel.ts:610`, `GridApi.refresh`, `dom/src/grid.ts:33`), a whole reload. `sameRow` (`rows.ts:147`) lets a reload keep unchanged rows' objects (`fresh-rows` flashes the changed ones). Edits on a server: `setReader` marks the server's order stale (`rows.ts:586-590`), `reapply` asks again (`:591-596`).
17. **The test bench for 10⁷ exists.** `perf/fake-server.ts` computes row *i* from *i* (« ten million rows cost nothing », l. 1–12), reads the wire form, answers pages and `values`, has `timers` and `hold` modes; `perf/permutation.ts` replays seeded gestures and answer orders against invariants (`audit-permutations.test.ts`, 1 000 permutations, 0 stale answer applied — §5.3 « Changement de page serveur (C) »).
18. **Angular.** `[source]` (`grid.ts:100`), `[busy]` (`:115`), `fromObservable` for an `HttpClient` source (`from-observable.ts:32-33`), `DzgController.refresh()` (`controller.ts:54-55`); `[(groupBy)]` exists. A block or server-side binding passes through `[source]` with no new input.
19. **Sehhaty.** ARCH §2.10 (l. 849–855) lists **no screen that needs infinite scroll**: `admin/audit-logs` (10⁵–10⁷) is server-paged and done (Phase 3); `pharma/history`, `labo/history` (15 k–150 k a year) are « server-paged or client, grouping maybe ». Server-side grouping would serve a grouped history on a server; infinite scroll serves a journal read by scrolling. Which one the owner needs first is Q-SE.
20. **Margins** (measured now, `node scripts/size.mjs` at `e6a1299`, gzip): core base **29 202 / 29 250 (48 B)**, dom base **23 282 / 23 290 (8 B)**, **K.8 audit profile 89 343 / 90 000 (657 B)**, `core/server` 6 137 / 6 200 (63 B; it is **inside K.8**: the audit screen imports `sourceRows`, `perf/audit-screen.ts:14`), `core/tree-lazy` 1 478 / 1 500, `dom/tree-lazy` 944 / 1 000, `core/grouping` 4 468 / 4 950, `dom/grouping` 4 648 / 5 100, `dom/pagination` 3 084 / 3 450, `dom/find` 2 569 / 2 650, `dom/print` 1 632 / 1 632 (0 B), `dom/range` 5 028 / 5 200, `ar-range` 500 / 500 (0 B), export run (lazy) 5 346 / 5 350, `core/csv` 2 040 / 2 040 (0 B), `core/state` 1 537 / 1 540, `dom/state` 1 233 / 1 240, theme 2 907 / 2 907 (0 B), `@dzgrid/angular` 7 803 / 7 810 (7 B). Owner's rule (Phase 7 Q-B, 2026-11-04): a new entry's line = its measure + 10 % at the close; an existing line moves by 2 % at most; beyond, the owner. **Any block code put in `core/server` lands in K.8** (the audit screen pays it without using it): block and server-side code must live in their own entries.

## 2. Decisions to take (D1…D18; the owner's answers win)

- **D1 entries.** (A ★) Two new optional entries, a server-paged grid pays nothing: `@dzgrid/core/infinite` (`infiniteRows(data, o)`: flat blocks) and `@dzgrid/core/server-side` (`serverSideRows(data, o)`: blocks per level, groups loaded on open, server totals). Both return a `SourceBinding` for the existing `source` setting (`kind: 'source'`, fact 1), share an internal block store (`core/src/server/blocks.ts`: cache, LRU, scheduler) and the parts of `server/rows.ts` they need (answer reading, the wire form and its cache, the request parts, `hold`) factored into internal modules **without growing `core/server`** (held at 6 200, fact 20). (B) one entry `server-side` that is flat when not grouped: a flat infinite grid would pay the levels (~1–1.5 kB). (C) a `blocks` option of `sourceRows`: lands in K.8 (fact 20). No new DOM entry for the flat case (D6); `dom/grouping` learns the server-side model (D13).
- **D2 the request and the answer.** (A ★) **The same `DataSource.fetch` and the same `DataRequest`**: a block is a `PageWindow` by offset (`index` = block number, `size` = block size, `offset` = first row, `cursor: null`); the answer is a `DataResponse` (`total` = the last row known, `hasNext` when the total is not). ARCH's `BlockRequest` / `lastRow` become these names (fact 2): a host that serves pages serves blocks unchanged. A request carries `blocks: true` (type only) so a host can tell them apart in its logs. `paging: 'cursor'` under blocks: `invalid-page` warning, read as offset (blocks jump). (B) a new `fetchBlock(req)` method with `startRow` / `endRow`: one more contract for every host.
- **D3 operations.** Under blocks everything is on the server: `operations` read as « all server » (a block is a cut of the final order, the rule of server pages, `operations.ts` header); a client placement is refused (`invalid-operations`, as today). `pagination` (the setting) ignored with `invalid-page` warning; the `pagination()` feature beside blocks: the pager is not drawn, the count part (« 1 234 567 lignes ») and the selection strip stay (Q-MODE).
- **D4 the virtual rows.** The model's `displayed` is a view over the block cache: `count` = the total when known; when not, the rows up to the furthest block answered plus one block of loading rows while `hasNext` (Q-END); `nodeAt(i)`: the data node from its block, else a **block loading node** `{ kind: 'loading', key: 'l:#' + i, level: 0, parent: null, failed }` (`LoadingNode.parent` becomes `RowKey | null`, types only; the tree's `l:` + parent keys cannot collide: `#` is never a key's first character after `l:`, keys start with a family letter). `indexOf(key)`: a `Map` over the rows held only (≤ `maxBlocks × blockSize`). A focus on a loading row stays on its position and goes to the data row that takes it (fact 7). `dataCount` = the data rows held. Version bumped on each block answered (a `rows` change, D9), never on a scroll.
- **D5 the cache.** An LRU of blocks across the whole model (and every level of D12), at most `maxBlocks` (Q-BLK); blocks **pinned while needed**: those that touch the window plus overscan, the focused row's, the anchor and focus of a cell range, an edited row's until saved; the least recently shown unpinned block goes first. A block holds `blockSize` rows by offset, its answer's `total` / `hasNext`, its epoch, its state (`asked` / `held` / `failed`). Diagnostics: `blocks.held`, `blocks.asked`, `blocks.evicted`, `blocks.max` (the high-water mark the exit criterion reads).
- **D6 asking for the window (DOM base seam).** After each paint the base tells the model its window: `rows.want?.(first, last)` (an optional `RowModel` method, types only in the core; ~20–30 B in the DOM base). The block store asks the blocks of the window, **then one block ahead** in the scroll direction (prefetch), at most **2 requests running** (more wait their turn, nearest the window first); while the scroll moves faster than one block per frame (thumb drag, PageDown held), nothing is asked until the window rests **60 ms**; a waiting block that left the window is dropped before it is asked, a running one is **left to finish** (its rows go to the cache) unless 2 newer ones wait — then cancelled (`gate.cancel('block:<n>')`). One gate channel per block, `block:<n>` (ARCH l. 1223). Overrides: `infiniteRows(data, { blockSize, maxBlocks, ahead, concurrency, restMs })`.
- **D7 loading rows on screen.** (A ★) The DOM base draws any loading node without a tree: `data-kind="loading"`, `aria-busy="true"`, its row header cell holds `grid.loading` (« Chargement… », base bundle, no new text), the other cells empty, muted by the theme (`--dzg-muted`); a failed block's rows: the first one says `grid.error` with the `grid.retry` button, the others are empty and say nothing (one Retry per block, as `tree-lazy.md`); Enter on it retries. Not data: never selected, copied, edited, exported, counted. Not announced while scrolling (only a user's Retry is said, as the tree). The tree painter keeps drawing its own loading rows (it runs after the base). (B) skeleton bars (grey shapes, still under reduced motion and in forced colours): +60–120 B theme, which has 0 B left. Q-LR.
- **D8 the busy state.** Block loads are **not** the model's `loading` phase (fact 10): `status` stays `idle` while blocks load under rows already shown, so no `data-stale`, no busy bar, no overlay — the loading rows say it. `loading` remains « the rows shown are being replaced »: the first load of an epoch (the overlay while nothing is shown, the first-load rule), a refresh (D10). A grid scrolled into loading rows has `aria-busy` on those rows only.
- **D9 purge on a new query.** A new epoch (filter, quick search, sort, params, zone, source, a server-side `groupBy`) drops **every** block, every waiting request (`gate.newEpoch`), counts and the end found; the view goes back to the top (Q-PURGE); the first block is asked at once and the overlay shows until it answers; the selection follows the existing rules (an everything-except tied to `membershipOf`: a sort keeps it, a filter change clears it unless `keepOnFilter`). An answer from an older epoch is dropped by the gate (`stale-epoch`), never cached.
- **D10 refresh.** (A ★) `refresh()` / Retry on the overlay: the blocks of the window are asked again with the rows kept (the busy bar: the rows shown are being replaced), every other block marked stale (asked again when shown, evicted first); `invalidate({ purge: true })`: everything dropped, the overlay. (B) every refresh purges. Q-PURGE.
- **D11 transactions.** The block and server-side models gain `applyTransaction(tx)` and `applyTransactionAsync(tx, done?)` (ARCH « transactions asynchrones groupées »): `update` / `patch` by id replace the rows **held** in place (a row not held is ignored: the server sends it when asked), nothing moves (K.14: a sort or filter column touched marks the order stale, `reapply` asks the window again); `add` / `remove`: the browser does not know where a new row falls nor how many rows shift, so the window's blocks are asked again with the rows kept and the others marked stale (D10 A), counts from the answer. Async: transactions gathered and applied once per `batchMs` (50 ms by default) or at the next frame, whichever comes first — one change, one paint, at most one refresh; `done(result)` per transaction. The grid opens no socket: the host listens to its server and calls these. Q-TX.
- **D12 the server-side model.** Levels: the root store (the top groups, or the rows when not grouped) and **one store per open group** (its child groups, or its leaves), each loaded in blocks of `blockSize` through D5's single LRU; displayed = the flatten of open stores, positions by a prefix sum over each store's count (the server's `count` for a group, else unknown and growing as in D4). A request is a `DataRequest` plus `group: { by, path, aggs }` — `by` the grouping column ids, `path` the **typed values** of the open groups from the top (a day as `YYYY-MM-DD`, an instant as epoch ms, null for the empty group; never a label or a key), `aggs` `[{ column, fn }]` with Phase 7's names (`sum`, `avg`, `min`, `max`, `count`, `first`, `last`) — plus the block window. The answer at a group level: `{ groups: [{ value, count?, aggs? }], total?, hasNext?, totals? }`; at the leaf level: `{ rows, total?, hasNext? }` (Q-WIRE). Keys: Phase 7's typed group keys (fact 14), so `rowExpanded`, open state and the painter are the client grouping's. **Totals come from the server only** (ARCH l. 1225): a custom aggregation function is refused (`agg-type`, detail `server`); footers show their group's `aggs`; the grand total row shows the root answer's `totals` when sent, else none (Q-TOT). Groups are never selected (Phase 7 Q-SEL A). Sort is the server's: the request's `sort` as sent; the sheet states the expected order (groups by value, reversed by a descending sort on their column, Phase 7 D7) as a contract, not a check.
- **D13 groups on open, and kept open.** Opening a group asks its store's first block (a loading row under it, then its children: the tree-lazy behaviour); closing keeps its store in the cache (evictable: reopening is instant while it lives). Across a new epoch the open set is kept (keys are values, Phase 7 D9): the open groups that come back are reopened and only those shown ask their children (Q-OPEN). `expandAll` opens the **groups held** to the depth asked, never a level not loaded (opening 10⁵ groups would ask 10⁵ requests): `rows.expandAll` refused beyond groups held with `unsupported-combination` detail `server`. `dom/grouping` on a server-side model: no client shape; `setBy` forwards to the model (a new epoch); the zone, the menu item, `[(groupBy)]` and `rowGroups` in the state work as on the client. On a plain `sourceRows` or `infiniteRows` grid, grouping stays refused (fact 14).
- **D14 selection.** As server pages (fact 12): `selectAll: 'query'`, `keeps: () => true`, `membershipOf` from the wire form (not the server-side `groupBy`: grouping changes how rows are shown, not which rows match). « Tout sélectionner » on 10⁷ rows = everything the query matches, sent to the host as the query and the exclusions (Q-SEL). Shift+click between two rows takes the **data rows held** between them (the loading rows have no key); a gap not loaded is refused: `selection-not-loaded` (info), the click's own row ticked. Under a selection rule (`gate.on`, fact 5), « all » takes the rows held, not 10⁷. Group rows never.
- **D15 every place that walks the rows** (fact 5; the review rule « every place that recomputes the same thing »). A virtual `displayed` gets an optional `held?(): Iterable<DisplayIndex>` (the positions of data rows held, in order); the eight walks use it when present: kernel `allDisplayed` / header state (rows held), Shift+click (D14), pagination strip (counts from the model, not a walk), row numbers (no walk: no details on blocks, D17), Ctrl+F (rows held, the bar says « lignes chargées »), print (rows held, Q-EX), CSV `displayed` (rows held, Q-EX). A test plants a 10⁷ `displayed` with a `nodeAt` that counts calls: each place must stay under 10⁴ calls.
- **D16 exports, print, copy.** (A ★) `all` and `selected`: the host's `exportAll` (as server pages; the `ExportRequest.server` gains the `group` part on a server-side grid, without the block); `displayed`: the rows held, in order (what the user has scrolled through, at most `maxBlocks × blockSize`), the request's `count` says so; print: the rows held, 5 000 at most (`print-too-many` above). Copy, cut, paste, fill and the status bar's totals over a cell range that crosses loading rows: **refused** with `range-not-loaded` (warning) and a sentence « Certaines lignes ne sont pas encore chargées » (`locales/*-range`, Q-COPY); inside rows held, as today. Ctrl+A with `range()` is a block of every row: copy refused above the rows held.
