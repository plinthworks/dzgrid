# Parts: what a host draws in the grid

## What the user does
Nothing different: they scroll, sort and filter a grid whose cells hold a badge, a button, a link drawn by the host's own code.

## What they observe
- The custom cells look the same as the rows scroll by; nothing flickers, a button keeps its focus while the list moves.
- One broken cell drawing does not blank the grid: that cell is empty, the rest paints.
- Sorting, filtering, quick search, CSV and right-to-left work on those columns as on the others.

## What DzGrid does
- **One contract for every slot:** a part is `mount(host, context)`, which returns a handle with `update(context)`, `destroy()` and `focus()`, each optional. The grid gives the host element; the part writes its own DOM. The grid never writes HTML.
- **Mount once, update on rebinding:** a part mounts once into a pooled cell. When the cell shows another row, new data, takes or loses the focus, or gets a new language, direction, column definition or message bundle, the grid calls `update` on the same handle; nothing else calls it.
- **Destroyed before its host moves:** when its column leaves the row's window, when the registry gives the column another part, and on the grid's `destroy` (pooled and spare cells included). Then the grid gives the cell back its plain text. Mounts equal destroys at the end.
- **Pooled rows keep their parts** while off screen, until they are rebound to a row; the grid itself holds no row data for them.
- **Context:** `value` (coerced by the column's codec, null when blank or unreadable), `text` (what the grid would show), `row`, `key`, `column`, `focused`, plus `ctx`, `dir`, `msg`, `announce` and `doc`.
- **By name, per grid:** `settings.parts` is one registry per grid, a plain record of `definePart(slot, part)` entries; no global registry, so several grids and SSR stay safe. It is live: a new record re-resolves every column, remounting what changed and going back to plain text for what lost its part.
- **How a column finds its part:** its own name (`ui.cell`, later `ui.header`, `ui.tooltip`), else `${slot}.${type}` (`cell.number`), else the built-in. Filters use the column's kind: `filter.kind`, or the type, an enum being `set` (`filter.set`, `floating.set`).
- **No part, fast path:** a column with no part keeps the grid's text path. Registering `cell.text` moves every text column to parts, on purpose.
- **`unknown-part`:** a name no one registered for that slot is an error problem at `columns.<id>.ui.<slot>`, told once per registry (not again on every resize); the column takes the type default or the plain text.
- **A part that throws** (in `mount` or `update`) costs its cell for that row only: the part is destroyed, the cell left empty, the error passed to `reportError`. It is not tried again on that row until the row's data changes; the next row the cell shows mounts it afresh. A `destroy` that throws is reported the same way and never stops the grid.
- **Focus:** focus inside a part survives scrolling, because the focused row is retained in place. A control a part draws (a button, a focusable span) owns its keys (`cell-widget`): arrows do not move the grid's focus.
- **Slots:** `cell` in the base; `header`, `overlay` and `tooltip` with the feature `slots()` from `@dzgrid/dom/slots` (step 11); `floating` with `filters()` from `@dzgrid/dom/filters` (step 12); then `filter`, then `footer` (`footer.pager`, `footer.count`, `footer.selected`). `editor` is Phase 4. Angular templates and components become entries of the same registry.
- **Header, overlay and tooltip (step 11, decision O1):** the base keeps its own header label, overlay message (with its retry button) and tooltip text, with no part machinery; `slots()` lets a host's parts replace them. Same `Part` contract, same throw rule: a part that throws in `mount` or `update` is destroyed, its host shows the grid's own text again, the error goes to `reportError`, and it is not tried again until its context changes.
  - **`header`** (per column) draws the label's content only (decision O4). The grid keeps `role="columnheader"`, `aria-colindex`, `aria-sort`, the name with the sort precedence, the sort mark, the resize grip, `dzg-sortable` and click-to-sort; a click on a control the part draws (a button, a link, `data-dzg-owner`) does not sort. Context: `column`, `label` (the column's `header`, or its id), `sort` (this column's sort item or null), `sortIndex` (its precedence from 0, or null), `toggleSort(multi)` (a `sort.toggle` by the user, Shift's behaviour when `multi`). `update` runs only when one of them, the language, the direction or the messages changed. The rows a feature adds under the headers and the group rows never take it. The filter button and the active filter mark (step 13) are decorations beside the sort mark, never part content.
  - **`overlay`** (one per grid): context `phase` (`loading`, `empty`, `no-match`, `error`), `failure`, `retry()`, `clearFilters()` (`overlays.md`).
  - **`tooltip`** (per column): context `text`, `value`, `row`, `column` (`tooltips.md`); shown only when the host gives text.
  - **Resolution:** a name is looked up among that slot's parts only. Header: `ui.header`, `header.<type>`, the bare name `header` (every column), then the built-in. Tooltip: `ui.tooltip`, `tooltip.<type>`, `tooltip`, then the built-in. Overlay: `overlay`, then the built-in. An unknown `ui.header` or `ui.tooltip` is `unknown-part`, told once per registry, and the next choice is taken.
  - **Without its feature:** a registered part whose slot needs a feature the grid lacks is `missing-feature` (warning, `parts.<name>`), told once when the grid is made, the detail naming the feature: `header`, `overlay`, `tooltip` → `slots`; `floating`, `filter` → `filters`; `footer` → `pagination`. The grid draws its own. A column asking for a floating filter or naming a `filter.kind` with no `filters()` is `missing-feature` at `columns[i].filter` (i over the leaves), detail `filters`.
  - **Lifecycle:** a header part is mounted with its header cell and destroyed when the cell leaves the column window, when its column gets another part, and on the grid's `destroy`; the overlay part when the overlay shows and hides; the tooltip part when the tooltip shows and hides. Mounts equal destroys at the end.

- **Parts a feature brings (step 12):** a feature may carry `parts` (`GridFeature.parts`), its defaults. The grid's registry is the features' parts (the first feature giving a name wins) under the host's `settings.parts` (a host's name always wins); it is read through `g.parts()`, the same object until `settings.parts` changes, so cells, headers, the overlay, tooltips and floating cells resolve from one place. A new `settings.parts` re-resolves them live. (`part-shadowed`, said when a host's name hides a feature's, waits for step 22.)
- **`floating`** (per column, `filters()`): context `column`, `kind` (the column's filter kind), `state` (built-in kinds: the column's stored filter; a custom kind: its `state`; null: none), `where` (`operations.filter`), `debounceMs`, and `set(next, { commit })` (`'debounced'` by default, `'now'` applies at once, `'cancel'` drops the column's pending edit when this part left it (a box giving way to the summary never drops the popup's) and stores nothing; null removes the filter; a custom kind's state is wrapped as `{type: 'custom', kind, state}`). Resolution: `floating.<kind>`, then the bare `floating` (the summary; a host's `floating` replaces it). A column with `filter: false`, an unknown explicit `filter.kind` (`invalid-filter`, detail `unknown kind`, at `columns.<id>.filter.kind`, once per registry), a custom type with no kind, or a custom kind with no `test` while the browser filters: an empty cell. `focus()` returns true when it took the focus (Enter or F2 on the cell). Same throw rule as the other slots: the cell left empty, the error reported, not tried again until the context changes. A column removed takes its pending edit with it (nothing dispatched). The part is mounted with its cell and destroyed when the cell leaves the column window, when the registry gives another part, and on `destroy`.
- **`filter`** (per column, `filters()`, step 13): the popup's content. Context: `column`, `kind`, `state`, `where`, `debounceMs` and `set` as `floating`'s (the same pending edit per column, the last write wins), `ops` (the column's `filter.ops`, empty when it gives none), `today` (the grid's day `YYYY-MM-DD` by its `clock` in its zone, step 14: new at midnight, so an open popup follows the day), and `close()` (closes the popup, focus back on its anchor, the pending edit applied in the browser). On a server (`where === 'server'`) a part keeps a draft and sends it at its Apply (owner decision O3). Resolution: `filter.<kind>` only, no bare `filter` fallback: a column has a popup when a part resolves (built-in `filter.text`, `filter.number`, `filter.boolean`; `filter.day` and `filter.instant` at step 14; `filter.set` at step 15, for a column whose `filter.kind` says `set` explicitly only: an enum column, set implicitly, gets no built-in popup (owner decision Q2), though a host's own `filter.set` part still resolves for it). Step 15: the context gains `values(o?)`, the column's `kernel.values(column, o)` handle (`value-list.md`); the part closes it when it goes (one handle per column: a host's own handle on the same column is closed by it). `floating` gains `canOpen` (the column has a popup) and `openFilter()` (opens it anchored to the cell's `aria-haspopup` control, or closes it when open).
- **`footer`** (`pagination()`, step 17, `pagination-footer.md`): the strip under the rows, one host per name listed in `pagination({ footer })` (default `footer.selected`, `footer.count`, `footer.pager`; a host's part of the same name replaces each, a host's dotless part may be listed). Context: `page` (the model's `PageState`, never null), `counts`, `status`, `range` (`{from, to}` from 1, null with no rows or while loading), `selection` (`count`: the last `selectionChanged` count, null when "all matching" is unknown; `shown`: selected rows on the page; `all`: an everything-except tied to the query; `canSelectAll`; `mode`), `go(i)`, `next()`, `prev()`, `setSize(n)` (`page.go` / `page.size` as the user; next and prev read the page at the call, and do nothing when there is none), `selectAll()` (`selection.allFiltered`), `clearSelection()`. The functions keep their identity, so `update` runs only when a value changed. The grid keeps the `<nav>` landmark and its name around `footer.pager`. No status region: the count is plain text, the page change is said through the grid's live region (`announce.page`).
- **Ready cell parts** (`@dzgrid/dom/parts`, step 20, `badge-boolean.md`): `badge({ tones, fallback })`, registered by the host under a name of its own and named in `ui.cell`, and `cellBoolean`, registered as `'cell.boolean'` (every boolean column). Plain cell parts on this contract: no feature, no setup, no style of their own (the theme's `.dzg-badge`, `.dzg-bool`, `.dzg-glyph`). Texts `cell.yes` / `cell.no` in `locales/<lang>-parts`; a bundle without them costs the yes/no cells (reported), nothing else. A per-cell class from the host (`ui.cellClass`) waits for step 26.
- **The application's context** (step 21, owner Q3): `settings.context` (any value, live) reaches every part as `context` in what every part gets (cell, header, overlay, tooltip, floating, filter, footer), the selection rule (`canSelect(row, selection, context)`), the export (`canExport(request, context)`, `exportAll`'s `context`) and the tooltip callback (`tooltip(value, row, context)`). A new value (a new identity) updates each part once; the same value updates nothing; a value changed in place is not seen (pass a new object). `context` is the application's; `ctx` stays the grid's language, zone and numerals. Not yet: filter kinds, value getters and the sort (Phase 4).
- **A header part driving the column filter** (step 21): with `filters()`, the `header` context gains `filter` (null without `filters()`, for `filter: false` or an unknown kind): `kind`, `state`, `where`, `debounceMs`, `dropped`, `set(next, { commit })`, `canOpen`, `openFilter()`, the same pending edit as the floating box and the popup (one per column, the last write wins). The object keeps its identity while its values stay the same (the part is not updated by unrelated paints); it is a new object when the column's filter in force, the column itself (a rename) or `dropped` changes. `dropped` (also on `floating` and `filter`, step 21 review) counts the edits this part left pending that another write dropped: the floating box or the popup writing the same column, or every filter written at once (clear all, a host's `filter.set` or `query.set`). When it changes the part's own edit is gone: it shows `state` again, even with text typed (the ready boxes do). Echoing the state while the part's own control has the focus is the part's duty, as for the floating box; so is the control's accessible name (`label`); the column header keeps its own name. A pending edit is applied when the column leaves the window. The seam: the filters feature hands `FeatureHandle.filter` (`edits`, `flush`); `slots()` reads it; neither imports the other.
- **`header.filterBox`** (step 21, optional, `filters()` with `slots()`): a ready header part a column names (`ui: { header: 'header.filterBox' }`): the column's name and, beside it, the floating row's control for its kind (text "contains", number "equals", any other kind the summary, which may open the popup), on the same pending edit. Without a filter, the name alone. A renamed column renames its box; a box whose edit another one replaced shows the filter in force.
- **Keys in a header cell holding a control** (step 21, shared with the floating row through `@dzgrid/dom/internal`): one tab stop (the control is out of the Tab order until the focus is inside); F2 enters (the part's `focus()`); Enter enters when the part's `focus()` returns true, and then does not sort (a keyboard sort goes through the part's own control and `toggleSort`); otherwise Enter sorts as before; Escape inside applies the pending edit and comes back to the header cell (inside an input method's composition it only ends it); Enter inside applies at once; the focus leaving the cell applies and takes the control out of the Tab order again. A click in the control never sorts.
- **Header decorations** (step 13): `FeatureHandle.decorateHeader(col, cell, label)`, called at each paint after the base decorated a column header (level 0): the filters feature adds its button and the filtered mark there, so a host's `header` part keeps them. `label` is the header's name so far (the sort's, or null); a feature returns the name to use (nothing: unchanged); the base writes it once after every feature, so a paint that changes nothing leaves `aria-label` alone.

## Decisions (step 1, 2026-10-17)
- **`update`, `destroy` and `focus` are all optional** (the code). A part without `update` keeps what it drew; without `destroy`, the grid only empties the host.
- **`msg` takes `MessageKey | app.${string}`.** An `app.*` key missing from the bundle gives the key itself and the warning `missing-message`, once per key. Step 0 follow-up.
- **The cell context gains `focused`**, true while the grid's focus is on that cell. Step 0 follow-up.
- **When `update` runs:** only when the context changed — another row key, new row data, `focused`, or what the context carries (language, zone, numerals, direction, messages, the column's definition). A rebind for the row height, the checkbox column or the column window calls nothing. Step 0 follow-up (`render/rows.ts` today calls `update` on every rebind).
- **Resolution:** the column's name, then `settings.parts`, then a feature's parts, then the built-in. Features gain `parts` at step 12, their first user (decision O8 of step 11; step 11 ships no default part).
- **A name registered for another slot** is `unknown-part`, as the code does: a name is looked up among the parts of that slot only.
- **A filter kind no one registered** gives `invalid-filter` and the column's filter is ignored. Step 8.
- **A `destroy` that throws** is reported through `reportError`, like `mount` and `update`, and the grid goes on. Step 0 follow-up.
- **Cell widgets:** the owner `cell-widget` is inferred from the control, as the code does; a part need not mark its container. Enter or F2 on a cell calls the part's `focus()`; when it is absent or returns false, focus stays on the cell. Escape returns to the cell (inside a host dialog, a first Escape returns to the cell, a second one reaches the dialog). Enter on a cell without a part is left to the host. Done (69b47fb).
