# The filter user interface

## What the user does
Types into a box under a column header; clicks the filter button in a header, or presses Alt+ArrowDown on it; picks an operator, a day, or ticks values in a list; presses Escape.

## What they observe
- A row of filter boxes under the headers, for the columns that ask for one: text and number columns get a box that filters as you type; the others get a summary button that opens the column's popup.
- The filter popup sits under the header and holds the column's filter: an operator and a value for text and number, all / yes / no for a boolean, an operator and one or two dates for a day or an instant, a searchable checklist for a value list.
- The value list has a search box, "select all (shown)" and "blanks". When the server filters, it waits for an Apply button; everywhere else a change applies at once.
- A filtered column shows a mark in its header, and its name says so.
- Escape closes the popup and puts focus back where it opened from. Inside a filter box, arrows, Home, End, Ctrl+A, Enter and Space edit the text and never move through the grid.
- The new row count is announced.

## What DzGrid does
- Matching rules are not repeated here: see `filter-text.md`, `filter-number.md`, `filter-day.md`, `filter-instant.md`, `filter-misc.md`.
- **Floating row** (step 12, `@dzgrid/dom/filters`): off by default, turned on per column (`filter.floating: true`) or for the grid (`filters({ floating: true })`); `filter.floating: false` keeps one column out. The row is fixed when the grid is made (owner decision O3): it exists when the grid option is on or any column, hidden ones included, asks for it; a column without a floating filter gets an empty cell, so every header row holds the same columns. It is a header row (counted in `aria-rowcount` and `aria-rowindex`), its cells `role="gridcell"` at level 1 of the grid's roving order: Down from a column header goes to it, then to the first row; Up comes back the same way, through the group rows above. Enter or F2 on the cell goes into its control (the box's text selected), Escape inside goes back to the cell and keeps the filter; Escape inside an input method's composition only ends the composition (it goes no further than the cell, applies nothing, the focus stays), and Enter there is the input method's. Inside the box (`data-dzg-owner="filter-input"`) arrows, Home, End, Ctrl+A, Space and Enter stay in the box; Enter applies at once and stays. The controls of a floating cell are out of the Tab order (one tab stop for the grid) until Enter or F2. A click there never sorts, shows no tooltip, has no resize grip.
- **The box:** `type="text"` (never `type=number`), `autocomplete="off"`, no spell check, no placeholder, named `filter.inputLabel {column}`; a number box has `inputmode="decimal"`. Its cell carries `aria-readonly="false"` (the grid says read-only). The text follows its own direction (`dir="auto"`, `unicode-bidi: plaintext`, aligned at the start).
- **What the box edits** (owner decision O3): a text box edits "contains" (null or `{type: 'text', op: 'contains'}`, keeping `caseSensitive`); a number box edits "equals" (null or `{type: 'number', op: 'equals'}`). Any other filter on that column (another operator, between, blank, a combined filter) shows the summary instead.
- **Live apply with a pause:** 300 ms when the filter runs on the server, 150 ms in the browser; `filter.debounceMs` on the column, then `filters({ debounceMs })`, override it (not a finite number of 0 or more: the default). One pending edit per column, replaced by the next; Enter, Escape, leaving the cell and the cell leaving the window apply it at once; destroying the grid drops it. An emptied box removes the column's filter (the built-in boxes never store an empty filter). Text is applied as typed (no trim). Typing in an input method applies when the composition ends. Enter and Escape inside a composition do nothing else, read as `isComposing` or a key of code 229 (Safari sends the composition's end before its last Enter, step 16): the same rule as the quick search box (`quick-search-box.md`), whose Enter applies at once and whose Escape empties it.
- **Numbers:** read in the grid's locale (`readNumber`): `1,5` in French, `١٫٥` in Arabic, `1.5` in `ar-SA` (refused in `ar-DZ`, where `.` groups thousands: `1.234` is 1234 there), `12%` as 0.12. A text is read once, when typed, in the locale of that moment. A number that cannot be read is not applied (the filter in force stays, and an edit still pending is dropped); it is judged when the edit would apply, not per keystroke (`-` on the way to `-5` is not flagged): the box gets `aria-invalid="true"`, a 2 px outline (not only a colour) and one announcement `filter.invalid {column}`; typing again clears it. Inside an input method, Enter and Escape judge nothing.
- **Echo:** the box keeps the form it last sent; the same filter coming back leaves the text alone (`1,50` is not rewritten under the caret). Another filter (the host's `filter.set`, Clear, the overlay's clear-all) rewrites it, a number in the locale without grouping; text typed and not yet applied is left alone. A locale change rewrites a box with nothing pending in the new locale (marks cleared). Text that ends on the filter in force (typed then erased, the same text again) has nothing to apply: no edit stays pending, and a later change from elsewhere shows. An edit pending when the box gives way to the summary (the host set a filter it cannot edit), when the column changes kind, or when the column is removed is dropped, never applied.
- **On a server:** only the pause differs; an empty edit on an unfiltered column and an unreadable number send nothing; an everything-except selection follows the kernel's rule (`server-selection.md`).
- **Summary** (step 12, owner decision O4; still so for dates at step 14: an inline date field would load tzslot with the row): for day, instant, boolean, set and custom kinds without a `floating.<kind>` part, and for a filter the box cannot edit. With a filter in force: the short, static text `filter.summaryActive` ("Filter active") and a Clear button named `filter.clear {column}` that removes the column's filter at once and puts focus back on the cell; without one, an empty cell. Step 13: when the column has a popup, the text is a button opening it (`aria-haspopup="dialog"`, `aria-expanded` while open, out of the Tab order like every control of the row), the popup anchored to it; Clear stays beside it. Without a popup it stays plain text.
- **Popup** (step 13): opened by the header filter button (a target of at least 24 px, after the label and the sort mark, clear of the resize grip; `tabindex=-1`, so the header keeps one tab stop; named `filter.popupLabel {column}`, `aria-haspopup="dialog"`, `aria-expanded`), by Alt+ArrowDown (no Ctrl, Meta or Shift) on a header cell or a floating cell itself (handled by the filters feature, not a core intent: decision O2; nothing inside a floating box, on a body cell or on a column without a popup), by a floating summary, or by `openFilter(column)` on the feature. Clicking the button never sorts; clicking it again closes the popup; another opener replaces it (one per grid). A column has a popup when a `filter.<kind>` part resolves: text, number and boolean at step 13, day and instant at step 14, set at step 15 (explicit `filter.kind` only); `filters({ popup: false })` turns buttons and popup off. Header cells with a popup carry `aria-keyshortcuts="Alt+ArrowDown"`, and their own name as `aria-label` (so the button's name does not join it).
- **What it holds:** visible labels on every field, native controls, no placeholder. Text: an operator (`filter.op`, the eight text operators or the column's `filter.ops` in its order) and a value (`filter.value`), hidden for blank and not blank. Number: the nine number operators, `between` adding `filter.valueTo`. Boolean: All / Yes / No. Day and instant (step 14): an operator and tzslot's date, period or moment field (`filter-date-picker.md`). A filter the form cannot show (combined, another operator, another type) shows "Filter active". A footer: Clear (`filter.clear {column}`, empties the form) and Apply (`filter.apply`). AND/OR, a second condition and the match-case checkbox wait for Phase 5 (decision O4).
- **Apply** (decision O3): in the browser the popup is live: typed text after the pause, a choice (operator, radio, Clear) at once; Apply and Enter apply what is pending and close; Escape closes and keeps it (applied). On a server the form is a draft: nothing is sent until Apply or Enter, one request; closing without Apply drops it. Popup and floating box share one pending edit per column (the last write wins); opening applies the box's; a box giving way to the summary drops only its own edit, never the popup's. A number that does not read is never sent: in the browser it is judged after the pause, at Apply or Enter it is marked (`aria-invalid`), said once (`filter.invalid`), focused, and the popup stays. A filter set from elsewhere while it is open rewrites a form not being edited and leaves one being edited alone.
- **A draft that cannot filter yet** (lead decision L1): an operator or an edit that leaves the form inactive (between with one bound, a value operator with an empty value) never removes the filter in force: the pending edit is dropped and the filter stays until the draft can filter or the user presses Clear (or All for a boolean). Escape then leaves the old filter; Apply and Enter close and keep it too (on a server nothing is sent). Clear always removes it, a pending edit of the floating box's included.
- **Read once:** a value is read when typed, in the locale of that moment (as the floating box). Apply reads it in that locale: a locale switch between typing and Apply changes nothing (no mark, no announcement; the edit pending and Apply agree). A locale change redraws a form not being edited in the new locale; one being edited keeps its texts and their reading.
- **Operators redefined while open** (the column's `filter.ops`): the operator chosen stays when still offered; otherwise the form shows the first one and its draft is what it now shows (Apply stores that; nothing is applied before). An operator in force no longer offered shows the summary.
- **Closing:** Apply, Escape, the button again, a pointer down outside it (owner decision Q4 of step 18, revising step 13's O7). A pointer down outside closes it as Escape does: in the browser the typed filter is kept (the pending edit applied), on a server an unapplied draft is dropped; the focus goes where the press puts it (never stolen back), and back to the anchor only when it lands on nothing focusable. A press on the control that toggles it is left to its click (the button toggles): the header's filter button, or the floating summary button. That control alone counts as the anchor for this rule, also when the popup opened with Alt+ArrowDown and is placed under the whole cell (lead decision, step 18 follow-up): a press on the same header's sort label, its resize grip or the cell itself closes it, and so does a press in a floating cell's box (that cell has no such control). a press inside the popup, a tzslot panel inside it included, keeps it open. An anchor that leaves the page while its cell stays (a floating summary emptied by All or Clear in the popup it opened) gives way to that cell: the popup stays, the focus in it, and goes back to the cell when it closes. It closes when the anchor's cell leaves the page or its column the column window, when the column's part changes, goes (hidden, `filter: false`, another kind) or throws, when the grid's direction changes, and with the grid (nothing applied, no focus moved, nothing dispatched then). Focus goes back to the anchor (the button, the header cell after Alt+ArrowDown, the summary button), else to where the grid's focus now is (a hidden column's focus moved by the grid: the next header), never the page's body.
- **Out of the window:** a column outside the column window does not open its popup. Alt+ArrowDown on a header kept mounted for the focus while scrolled out of view does nothing and is left to the page (not handled); the user scrolls it back first. Chosen over scrolling it into view: smaller, and the popup never opens off screen.
- **Value list** (step 15, `filter-set.md`): only on a column with an explicit `filter: { kind: 'set' }` (owner decision Q2: an enum column, set only implicitly, keeps no button and no popup). A `listbox` with `aria-multiselectable`, always windowed (2 000 values at most, the core's cap, then `filter.set.truncated`), `aria-setsize` and `aria-posinset` on every option. On a complete list (no search, not truncated) ticking more than half gives `exclude`, fewer gives `include`, a tie keeps the mode; unticking everything stores `include: []` (owner decision Q1); the search narrows the list, never the filter. Values come from the rows held when the filter runs in the browser (counts over the other filters and the browser's search, never this column's own), from the source's `values()` when it runs on the server (never from the rows held; a stale answer is dropped), or from `enumOptions` when the server has no `values`. A value with no row is not offered, except one already ticked (`value-list.md`). The list is a lazy chunk, loaded on first use.
- **Day and instant** (step 14, owner decisions Q1, Q4): tzslot 2.2.0's fields, loaded on first use, an optional peer; no native date input (`filter-date-picker.md`). A wall time that a clock change skips is moved to the first moment that exists, with tzslot's note; a repeated one takes the first reading, a button the second. The shortcuts (*today*, *last 7 days*…) sit under *between* / *between days* (`filter-relative.md`).
- **Top layer:** the popup is shown with `popover="manual"` when the browser has it, `position: fixed` in the grid otherwise, so a host card with `overflow` or `transform` cannot clip it. It is a modal `dialog`: focus goes in, Tab stays inside; a pointer down outside closes it (Q4 of step 18, above). Escape closes it without reaching a host dialog around the grid, and focus goes back to the anchor; if the anchor left the page (header recycled, column hidden), the popup closes and focus returns to the grid's focused cell.
- **Keys:** a filter box carries `data-dzg-owner="filter-input"` and owns every key; popup controls carry `popup`. A grid inside a host popup still owns its own keys.
- **RTL:** the popup's start edge lines up with the anchor's start edge, on the right in Arabic, and it opens above when there is no room below. It carries the grid's `dir`; inputs follow the logical order.
- **Active mark:** `data-dzg-filtered` on the header and `header.withFilter {header}` as its name ("Amount, filtered"), joined after `header.withSort` when both hold; the theme fills the funnel of the button (a shape, not only a colour).
- **Button and mark are decorations** (step 11, decision O4): the filters feature puts the filter button and the active mark in the header cell beside the sort mark, through a header decoration seam (`FeatureHandle.decorateHeader`, step 13). They are never the content of a `header` part, so a host's header part keeps them.
- **Announcements:** after a user's filter change, `announce.filtered {rows}` with the filtered count (`announce.rows`); on a server, once the answer is in (a failed fetch says nothing more); `announce.filteredOpen` when the count is unknown.
- **Texts in their own bundles** (owner decision O1): `@dzgrid/dom/locales/{en,fr,ar}-filters`, spread by the host into its messages (`text: { ...FR.text, ...FR_FILTERS.text }`); the base bundles do not grow. `filters()` throws a `TypeError` naming any missing filter key when the grid is made.
- **Clear all** (the overlay's `clearFilters()`): one `query.set` keeping the sort, so a server is asked once.

## Decisions (step 1, 2026-10-17)
- **Names:** the floating row is `filter.floating` per column and `filters({ floating })` for the grid; the date picker was to be `filters({ datePicker })` (superseded at step 14: tzslot is the control, `filters({ loadDates, dateMessages })`). The plan's `floatingFilter` and `adapter` are superseded.
- **Apply button** whenever `filter` runs on the server, fetched set included (B5.6). Pending ticks stay pending until Apply; closing the popup discards them.
- **Where focus returns:** to the popup's anchor — the filter button when it opened from it, the header cell after Alt+ArrowDown. If the anchor left the page, the grid's focused cell.
- **Popup name:** `aria-label`, as the popup host does, from the new key `filter.popupLabel {column}`. No `aria-labelledby` on the header text: the header can be recycled and its name carries the sort state.
- **Initial focus:** the filter part's `focus()` when it returns true, else the first focusable control (the popup host's default). The filters feature calls it after mounting the part.
- **Pointer down outside** a filter popup does not close it (it is modal, as the code does); nothing pending is applied. *(Superseded at step 18, owner decision Q4: it closes, as Escape; see Closing above.)*
- **Summary text:** (superseded at step 15, owner decision Q4: a value list keeps `filter.summaryActive`, no `filter.summarySelected`) a value list reads `filter.summarySelected {n}` (plural); every other kind `filter.summaryActive {column}` when active and `filter.summaryNone {column}` when not.
- **Header name:** the filtered state joins the name through `header.withFilter {header}`, applied after `header.withSort` when both hold; `aria-label` is set only when one of them holds, as today.
- **Announcement on a server:** after the accepted answer, `announce.filtered {rows}` with `counts.filtered`; when the server does not know the count, `announce.filteredOpen`. Nothing is said while it loads beyond `aria-busy`.
- **Clear all filters:** only the no-match overlay's `clearFilters()` in Phase 3; a host clears with `filter.set {}`.
- **Escape in a floating box** returns focus to its cell and keeps the typed filter; tested at step 12.
