# Step 14 decisions (owner and lead, 2026-10-19) — date filters

Plan: `step14-dates-blueprint.md` (first plan, native inputs) is superseded on the controls by these decisions; a second architect pass writes `step14-tzslot-blueprint.md`.

- Q1 (owner): « il faut utiliser tzslot » — the date filters use the owner's library tzslot 2.2.0 (`~/Dev/tzslot`, a sister project, allowed by CLEANROOM): `@tzslot/dom` `createDateField`, `createDateTimeField`, `createRangeField` (named ranges). Then (owner, "tzslot obligatoire"): tzslot is the date control of DzGrid's filters, not an optional adapter; step 21 (`/tzslot-picker`) is folded into step 14. The native `input type=date` is not used.
- Measured by the lead (2026-10-19, esbuild minify + gzip of tzslot 2.2.0 dist): date field alone about 11 kB gz without the Temporal polyfill; the three fields about 40 kB; the Temporal polyfill about 23 kB more (static import in `@tzslot/core`). Today's audit screen sums to about 64 kB gz (72 with spans) against the 85 kB ceiling (K.8): with tzslot loaded, the ceiling is passed. Owner told plainly; Sehhaty does not (or not known to) load tzslot already. Lead proposal for the architect: load tzslot only when a date filter is first opened (dynamic import), so grids without date filters pay nothing and the audit screen pays it on first use; the K.8 ceiling is revisited with the owner at step 18 with real measures.
- Q2 (owner, "Oui"): `@dzgrid/dom/filters` 7 000 → 8 500 B gz, filter bundles en 680 / fr 760 / ar 850, theme 1 520 → 1 600 (for the DzGrid side; tzslot's own size counted separately).
- Q3 (owner, "Maintenant", then "Relatifs, recalculés"): date shortcuts (today, last 7 days, this month…) now, as relative filters kept in the model and resolved in the grid's zone when filtering; the server gets the exact range (and the shortcut's name). This is a core change (new model variant, compile, toWire, conformance cases); expected core budget 26 100 → about 26 400 (to confirm with the measure).

Second plan (`step14-tzslot-blueprint.md`, 2026-10-19), owner answers:
- Q4 (owner, "Non, seulement si dates"): `@tzslot/dom` and `@tzslot/core` (>=2.2.0 <3) are optional peer dependencies of `@dzgrid/dom` (and `@dzgrid/angular`): an application with date filters installs them; without them a date filter shows "calendar unavailable" (no other control). tzslot is loaded on the first opening of a date filter (three lazy kits: date, range, moment).
- Q5 (owner, "Oui, ces six"): shortcuts today, yesterday, last7Days, last30Days, thisMonth, lastMonth (tzslot's names and semantics); in the whole-day range forms only (day between, instant betweenDays), not in the between-two-times form; no "this week".
- Q6 (owner, "Oui"): during Phase 3, reset to the measure + 10 % at the close: core 26 100 → 26 900; theme 1 600 → 1 660; new entry "date adapters (lazy)" 2 600 B gz (DzGrid code only, tzslot external); filters 8 500 and filter bundles en 680 / fr 760 / ar 850 unchanged; tzslot's own kits recorded apart (no budget).
- Q7 (owner, "Oui"): if a kit fails to load: a message and Retry; blank / not blank, Clear and Escape still work; the filter in force stays.
- Lead decisions: §6 of the blueprint (eager/lazy split with its own budget line; K.8 counts the initial load, kits beside it, revisited at step 18; midnight timer in the filters feature, `kernel.tick()` otherwise; `filters({ loadDates })` advanced; `clock` setting; closed wire op set plus `relative` and `zone`; "today" on a Day column in the grid's zone; `readingStyle: 'named'`). A skipped wall time is moved later with tzslot's notice and a repeated one takes the first reading with a button for the second (tzslot's behaviour; reverses the first plan's refusal).
- tzslot requests for the owner (T1, T8, T3, T2, T6, T4) are listed in the blueprint §6; each has a workaround in our adapters.
